# Operations and incidents

The owner must name a real support/on-call contact and confirm the SNS alert subscription before launch (B07/B08). No email, paging notification or incident drill has been sent in this build. Support tickets persist in the account database; notifications/mailbox integration remain pending. Operations and support roles are separate; MFA codes are one use per time step and changes append audit records. Initial operator enrollment must be performed through a protected owner migration after verifying the account ID; never through a public signup parameter.

AI-cost or abuse incident: use the MFA `/v1/operator/controls` route to disable provider/runner admission, record incident ID/time/source version, inspect spend_days/holds and job state by IDs. Local comment removal/PDF remain available. Unknown provider acceptance retains its hold and is never automatically sent twice. Reconcile the provider invoice before releasing/settling uncertain work. Do not delete ledger rows. Budget alarms alone do not stop charges; admission controls do. Raise ceilings only with approved prices and measured cost.

Runner incident: set runner_enabled=false, drain fleet to zero after running jobs reach a bounded deadline, mark abandoned running jobs uncertain and never blindly redispatch. Rebuild the baked host/image with fixed runtime/kernel/runsc, scan and rerun functional/network/resource/residue probes. Rotate the signing key if gateway trust is in doubt. Public verification key alone cannot mint jobs. Enable a single canary host before general admission. The application database is never mounted or configured on runner hosts.

Payment incident: disable BILLING_RELEASE_APPROVED, preserve signed-event IDs/checksums, inspect checkout intents and provider transactions. Confirm customer/subscription ownership against billing_links. Replayed events must not duplicate grants. Chargebacks mark entitlement past due and record adjustments without erasing ledger history. Refund/proration policies and administrative correction UI are not launch-ready; require owner-approved decisions and merchant sandbox rehearsal. Never retry an uncertain transaction creation as a new purchase.

Database/storage incident: stop writes if integrity is uncertain, preserve audit, use the recovery runbook. Object deletion denies access immediately and queues removal; failed cleanup remains inspectable. Monitor dead jobs and stale queue age. For quarantine/extraction, reject unsafe input instead of broadening parser limits under load.

Availability incident: inspect ALB 5xx, target health, ECS rollout/circuit breaker, RDS connections/CPU and queue age; rollback by digest if a release caused the failure. Test CloudFront dynamic no-cache and origin restrictions before re-enabling service. API metadata logs deliberately omit request bodies, cookies, query tokens and code. Dashboards/latency/custom financial alarm wiring and observed notifications still need staging verification.

Scheduled owner operations after launch: daily financial exception query and provider/merchant reconciliation; daily dead-letter and bounce/complaint review; weekly supported-runtime/dependency security update review; monthly restore/rollback sample; review country performance and costs before expansion. Record actual exceptions, owner and resolution. No post-launch period exists yet, so REL-006 remains Partial.
