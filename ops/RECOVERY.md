# Recovery, rollback and deletion

Current evidence: clean/upgrade migrations and local persistent PostgreSQL WASM restart pass. AWS Backup/RDS retained recovery resources synthesize. No RDS PITR, S3 restoration, regional recovery or live rollback has been performed. B01/B02/B05/B09 apply.

Proposed targets for owner review: 15-minute RPO for the database; 60-minute RTO for staging drill; 35-day production database recovery window. S3 object version recovery depends on backup readiness and region. These are targets, not promises. A second-region backup/copy policy and tested key recovery are still required for regional disaster recovery.

Drill on a separate staging restore, never overwrite the live database. Record `incidentAt`, begin time and recovery-point ARNs in `restore-record.example.json`. Select a known pre-incident RDS PITR point; restore to a new isolated DB. Restore corresponding private S3 versions/recovery point with the correct KMS key and denied public access. Keep providers, billing dispatch and runner kill switches off. Run migrations only if compatible with the restored version; verify migration checksums first. Restore deployment images by recorded digest and supply fresh scoped task secrets.

Before enabling service, run account A/B negative ownership checks, login/session rotation, file checksums and `check-finance.sql`. Compare merchant event IDs and provider usage to external authoritative records since the recovery point. Do not issue new credits for unknown dispatch or replay an uncertain checkout. Replay only verified missing merchant events through the signed adapter or a reviewed correction that appends ledger history. Restore deletion tombstones/current deletion requests before permitting restored users or exports; a backup must not resurrect access for a previously deleted account. Test one unaffected account and one deleted account. Record the latest recovered committed write and service-ready time, then compute measured RPO/RTO. Failure keeps the drill gate open.

Rollback is application-version rollback, not automatic schema reversal. Use additive, forward-compatible migrations; retain previous task definitions and immutable images. The ECS rollout helper requests old task definitions if wait/smoke fails. Confirm healthy tasks, no new 5xx, queue stability and compatible schema. If the migration is destructive or previous app incompatible, pause costly services and use a forward repair or separately rehearsed restoration. Never restore a production DB solely to undo CSS/application code.

Backup confidentiality: KMS keys retained, backups private, restore capability limited to a separate audited operator role, CloudTrail reviewed. Application user deletion removes active content asynchronously; minimal immutable financial/security metadata and encrypted backups may remain under approved retention. Final backup expiry and deletion disclosure require B08 owner review. No claim of immediate erasure from backups/provider systems is published.
